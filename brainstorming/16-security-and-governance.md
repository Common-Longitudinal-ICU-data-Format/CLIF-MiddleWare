# Security and governance: who may do this, and how we don't lose the keys or the patients

*The cryptography is the easy part; the paperwork and the private key are what actually block a hospital deployment — and the scariest failure mode is a well-meaning engineer pasting flowsheet names into a chatbot.*

## In plain words

This service holds two things that can end a project: a private key that unlocks a hospital's patient data, and the patient data itself. Everything below is about not losing either one, and about being allowed to touch them at all.

Three governance ideas run underneath all of it, and none of them are technical.

**HIPAA "minimum necessary."** The law says: when you handle protected health information, ask for the least you need to do the job, not everything you could get. For us that means requesting narrow scopes, narrow resource types, and narrow filters on export — and being able to explain, on paper, why each data element we pull is required by the research question. "We grabbed everything because it was easier" is the posture the rule exists to forbid.

**Business Associate Agreement (BAA).** A hospital is a "covered entity" under HIPAA. The moment an outside party touches its PHI, that party becomes a "business associate," and a BAA is the signed contract that binds the business associate to protect the data, use it only for the agreed purpose, and report breaches. If we (the vendor) run this service or hold the key, we are a business associate and we need a BAA. If a component we use — say a hosted language model — touches PHI, that vendor needs to be under a BAA too, or it cannot legally see the data.

**IRB (Institutional Review Board) and the research-vs-operations line.** A hospital may use and share PHI for "treatment, payment, and operations" without asking each patient. Research is different: pulling patient data in bulk to build a research warehouse normally requires IRB approval and a data-use determination, and sometimes a waiver of consent. Because our stated purpose is research — not clinical care, not billing — we live on the research side of that line, and that means an IRB has to bless the plan before any PHI moves. In practice, the IRB and the key-custody story, not the OAuth handshake, are what stall a deployment. See [doc 06](06-authentication.md) for the auth mechanics this section governs.

And the single scariest thing in this whole project is not a bug. It is that an engineer, trying in good faith to figure out what `VENT MODE 4` or `PRESSOR - LEVO` means, pastes a hospital's real flowsheet names into a public chatbot. That is a PHI egress event, it happens with the best intentions, and no firewall stops it. The rest of this doc exists partly to make sure that never has to happen.

## Technical detail

**Key custody.** Prefer systemd **`LoadCredential=` / `ImportCredential=`** with `systemd-creds`, optionally TPM-bound, so the private key is decrypted only into the unit's private `/run/credentials/<unit>` directory and never sits world-readable on disk ([systemd-creds](https://www.freedesktop.org/software/systemd/man/latest/systemd-creds.html), [`LoadCredential=`](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#LoadCredential=ID:PATH)). **[spec]** Alternatives, in rough order of operational weight: HashiCorp Vault issuing a short-lived token via Vault Agent; `sops` + `age` for encrypted-at-rest config ([sops](https://github.com/getsops/sops), [age](https://github.com/FiloSottile/age)); an HSM / TPM / PKCS#11 module holding a non-exportable key. **Never** bake the private key into a container image or commit it to a git repo — both are copied, cached, and shared far beyond where you think they live.

**Key rotation.** Publish a JWKS with multiple keys, each a distinct `kid`. Rotation is add-then-retire: publish the new key, start signing with the new `kid`, and retire the old key only after it has propagated. The complication is vendor policy: Epic and Cerner require **a different key per customer and per environment** (non-production vs production) ([Epic on FHIR](https://fhir.epic.com/)), so a vendor serving several hospitals is maintaining a key matrix — site × environment — that drifts unless it is managed as inventory. Epic sandbox key propagation is reported to take roughly 60 minutes, so allow for it in onboarding runbooks. **[community]**

**Audit logging.** Log every token acquisition (`jti`, granted scopes, timestamp), every export kickoff / poll / manifest download with file hashes, and every mapping approval — who approved, when, and what the prior value was. FHIR defines an [`AuditEvent`](https://hl7.org/fhir/auditevent.html) resource for this; a SIEM works equally well. **[spec]** The log must be tamper-evident: an audit trail an insider can silently rewrite is not an audit trail. This log is itself the evidence that "minimum necessary" was honored, so it is not optional paperwork.

**HIPAA minimum necessary, mechanically.** Request the narrowest scopes SMART v2 allows. Combine `.rs` (read/search) scopes with `?category=` granular scopes where supported (granular `category` scoping at Epic is **[unverified]**), and constrain the export itself with `_type` and `_typeFilter` ([Bulk Data export](https://hl7.org/fhir/uv/bulkdata/export/index.html)). Keep a written mapping from research question → requested data elements; that document is what an auditor or IRB asks for first. See [doc 12](12-clif-events-and-signals.md) for which signals we actually need, which bounds what we are entitled to request.

**PHI at rest.** Three artifacts are all PHI: the downloaded NDJSON, the `clif_events` log, and the CLIF warehouse itself (see [doc 11](11-middleware-architecture.md) for where each lives). Encrypt at rest — a LUKS/dm-crypt volume under everything, or app-level encryption, or both — restrict OS file permissions to the service user, and secure the database with its own auth. TLS end to end in transit. None of this is exotic; the failure mode is forgetting that the intermediate NDJSON dump is as sensitive as the warehouse.

**Governance and legal footing.** Running inside the hospital, the service operates either under the covered entity directly or as a **Business Associate** bound by a **BAA**. Bulk research use typically requires **IRB approval** plus a data-use determination, and the "treatment/operations vs research" distinction changes what is permissible without patient consent. This is an institutional question, not a technical one, and it must be settled **in writing before any PHI is pulled**.

**UDAP / TEFCA.** UDAP ([udap.org](https://www.udap.org/), [HL7 UDAP Security IG](https://hl7.org/fhir/us/udap-security/index.html)) is **not** required for a single hospital using static client registration — the SMART Backend Services flow we use registers the client out of band. UDAP becomes relevant only for cross-organization exchange: as of **Jan 1, 2026**, TEFCA "Facilitated FHIR" authentication SHALL use the FAST/UDAP SSRAA IG. **[spec]** Note that mTLS is generally **not** required by SMART Backend Services or by Epic/Cerner backend flows — they authenticate via the signed JWT, not a client certificate — though some enterprise API gateways bolt mTLS on at the network edge. Don't design assuming mTLS; don't be surprised if a given site's gateway demands it.

**The LLM as PHI egress (inference — flagged, and real, not theoretical).** The mapper engine (see [doc 12](12-clif-events-and-signals.md)) sends clinical signal names to a language model to propose CLIF mappings. If that model is a hosted API, PHI-adjacent strings leave the building on every call. Three mitigations, layered:

- (a) **Scope what the mapper sees.** It should only ever receive the **distinct signal catalog** — code, display name, unit — never patient rows, never identifiers, never observed values. This is a hard architectural boundary, not a convention.
- (b) **Prefer a locally-hosted model** so nothing leaves the network at all.
- (c) **If a hosted model is used, it must be under the BAA.** The doc should name which vendors offer a BAA for their API (e.g., major cloud AI providers offer BAAs for their enterprise tiers — confirm current terms per vendor; **[unverified]** as a standing fact because terms change).

The catch that makes this non-theoretical: a free-text `display` string can itself carry PHI. Real flowsheets contain rows like `"POTASSIUM - MRN 12345678"` or a nurse's free-typed patient note in a label field. So even the "safe" catalog of names needs a **scrub-and-review step before any egress** — automated pattern-stripping (MRN-shaped digits, name-shaped tokens) plus a human check on anything flagged. This is the concrete defense against the paste-into-a-chatbot scenario from *In plain words*: if the sanctioned path is easy and audited, the unsanctioned path is less tempting.

**Re-identification.** A CLIF warehouse carrying full timestamps, ADT transfer history, and rare diagnoses is **not** de-identified under HIPAA Safe Harbor ([Safe Harbor method, 45 CFR §164.514(b)(2)](https://www.hhs.gov/hipaa/for-professionals/privacy/special-topics/de-identification/index.html)) — dates more specific than year and geographic detail are exactly what Safe Harbor removes, and rare diagnoses plus a transfer timeline can single out an individual. Treat the warehouse as fully identifiable PHI, not as a de-identified dataset, in every governance conversation. **[spec]**

**Deleted resources (IRB-relevant).** The Bulk Data v2.0.0 manifest carries a `deleted[]` array for records the source retracted ([Bulk export manifest](https://hl7.org/fhir/uv/bulkdata/export/index.html#response---complete-status)), but EHR support for it is thin. **[spec]** for the manifest field; **[community]** that population is spotty. If the EHR repudiates a record and never tells us, our warehouse retains data the source system has withdrawn — a research dataset out of sync with the clinical record of truth. Flag this to the IRB explicitly; it is a data-provenance problem, not merely a sync bug.

**Who owns the private key (inference — recommendation).** Epic requires a per-customer key. If the **vendor** holds it, the vendor can read that hospital's PHI from anywhere the key can run — a concentration of risk that outlives any single deployment. Recommendation: **the hospital generates the keypair** and hands over only the public half; the service loads the private key at runtime via `LoadCredential=`, so the vendor never holds it and cannot exfiltrate data by copying a key. This also cleanly answers "whose key was it" after any incident.

**Separation of duties (inference).** The person who **approves** a clinical mapping must not be the same person who can **silently edit** the approved-map store. Approval is a clinical judgment that gets logged; the ability to change an approved mapping without re-approval turns the audit trail into fiction. Enforce it with roles: mapping-approver and store-admin are different grants, and every write to the approved-map store is logged against the approver's identity.

## Edge cases and how it breaks

- **The key ends up in a Docker layer.** Someone `COPY`s the config dir "just for the build," the key is now in an image layer cached in a registry. The image looks clean at `HEAD`; the layer history is not. Mitigation: key only ever arrives via `LoadCredential=` at runtime, never at build time, and CI scans images for key-shaped blobs.
- **Rotation matrix drift.** With N sites × 2 environments, a vendor eventually signs prod with a retired `kid`, or serves a JWKS missing the key a site expects. Symptom: intermittent `invalid_client` at one site only. Mitigation: treat keys as inventory with expiry dates and automated propagation checks; budget the ~60-minute Epic propagation window. **[community]**
- **The scrub misses a display string.** A flowsheet label like `"K+ f/u call pt 555-0134"` sails past a digit-only MRN filter. Mitigation: human review of anything with free-text characteristics, and a deny-by-default posture — unrecognized label shapes are held, not sent.
- **Audit log on the same disk as the data.** An attacker (or a `rm -rf`) that reaches the warehouse also reaches the evidence. Mitigation: ship audit events off-box to a SIEM as they happen; local log is a convenience copy, not the record.
- **Hosted LLM without a BAA, used "just for testing."** Test data is often real data. The moment a real `display` string hits a non-BAA endpoint, it is a reportable event. Mitigation: the mapper's egress target is config, and non-BAA endpoints are refused by the service, not by policy.
- **A narrow Group hides deletions.** If the site scopes our export to a Group, and `deleted[]` is unpopulated, records that leave the cohort (transferred out, corrected) may simply stop appearing with no tombstone — indistinguishable from "never existed." Warehouse quietly diverges from source.
- **"De-identified" claimed too early.** Someone downstream treats the warehouse as Safe Harbor de-identified and shares it more freely than the timestamps and rare diagnoses permit. This is a governance breach dressed as a convenience.

## What we still don't know

- Whether Epic actually honors granular `?category=` scopes such that we can request `laboratory` Observations without also being handed everything — the minimum-necessary story leans on this and it is **[unverified]**.
- Which specific hosted-LLM vendors will sign a BAA covering the mapper's use pattern, on what tier, and at what cost — terms change and must be confirmed per vendor at contract time.
- Whether a TPM is available and provisionable on the actual deployment host inside a given hospital, which determines whether we get TPM-bound `systemd-creds` or fall back to file-based credential encryption.
- How reliably any target EHR populates the Bulk manifest `deleted[]` array — thin support is reported **[community]**, but per-site behavior is unmeasured until we probe a real instance.
- Whether a given site's enterprise gateway adds mTLS on top of the JWT flow, which we would discover only during onboarding at that site.
- The exact IRB posture at each partner institution: whether bulk research export qualifies for a consent waiver, and how the IRB views the retained-after-deletion data-provenance issue. This is settled per site, in writing, and we cannot assume it generalizes.
